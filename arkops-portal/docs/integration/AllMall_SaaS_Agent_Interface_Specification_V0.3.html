AllMall SaaS-Agent Interface

SaaS 与 Agent 接口文档 V0.3

本文档定义 AllMall SaaS、Runtime Adapter、MuleRun、竞品定价 Agent 和运营数据 Agent 之间的统一协议。竞品 Agent 面向待上架新品输出可解释的建议价格；运营数据 Agent 同时支持店铺首次接入时的实体全量建档、后续增量同步，以及日常经营指标汇总。

Login Bootstrap Competitor Pricing Initial Full Sync Incremental Sync Daily Metrics Task Lease Checkpoint Resume
规范结论：所有 Agent 调用 SaaS 的接口统一使用 /api/agent/*。竞品定价 Agent 只输出建议价格，不自动上架或调价；运营数据 Agent 只读取和同步店铺实体及统计数据，不执行发货、退款、售后、评价回复、投放启停、活动报名、商品修改或库存调整。

2. 交互架构与任务投递

2.1 组件职责

组件职责禁止事项
AllMall Portal创建任务、展示状态、处理审批和展示结果。不得直接调用电商平台或持有 Agent Key。
AllMall SaaS租户隔离、任务状态、租约、回调、数据入库、审计。不得保存电商平台账号密码。
Runtime Adapter封装 MuleRun Create Session / Create Run / Resume Run。不得绕过 SaaS 业务状态机。
Agent使用绑定的 Browser Profile 执行任务并回传证据。不得跨租户或跨店铺复用 session。

2.2 两种任务投递模式

模式流程适用阶段
runtime_pushSaaS 经 Runtime Adapter 创建 Run，并把 Task Payload 传给 Agent；Agent 随后调用 Claim。产品化默认模式。
agent_pollAgent 调用 /api/agent/tasks/next 获取候选任务，再调用 Claim。Beta、定时 Worker 或 Runtime 不支持推送时。
无论采用哪种投递模式，Agent 都必须成功 Claim 后才能执行。Task Payload 本身不是执行授权，claimToken 才是当前 Agent 实例对该 Run 的租约凭证。

内部调用约束

  • SaaS 创建 Task / Run 成功后才可调用 Create Run；Runtime 接受不等于 Agent 已开始，仍需等待 Agent Claim 和 run_started。
  • Create Run 以 AllMall runId 幂等；相同 runId 不得创建两个 Provider Run。
  • Resume 和 Cancel 必须携带最新 controlVersion，旧版本指令返回冲突。
  • Runtime Adapter 只负责 Provider 翻译和状态映射，不写入业务实体或经营指标。

2.4 首次全量同步端到端时序

步骤方向动作状态结果
1Portal → SaaS用户请求同步已有店铺数据。创建 Sync / Task / Run，状态 queued。
2SaaS → Runtime Adapter调用 POST /internal/runtime/runs，投递 initial_full 载荷。保存 runtimeRunRef，等待 Agent。
3Agent → SaaSClaim Task 并回传 run_started。Run → running。
4Agent → SaaS按页调用 Entity Batch，必要时上传 Artifact。逐批更新 Checkpoint。
5Agent → SaaS回传经营指标批次。更新指标 Checkpoint。
6Agent → SaaS调用 Sync Complete。SaaS 校验并发布数据版本。
7Agent → SaaS完成接口成功后回传 run_completed。Task / Run → succeeded 或 partially_succeeded。
因此，该场景在业务上由 SaaS 发起，在传输上由 SaaS 主动启动 Runtime；大数据量结果通过多次批次接口返回，最终再由 Agent 调用完成接口收口。

3. 通用约定

3.1 Header

Authorization: Bearer <agent_access_token>
X-AllMall-Request-Id: req_20260717_001
X-AllMall-Idempotency-Key: idem_20260717_001
X-AllMall-Timestamp: 2026-07-17T10:30:00+08:00
X-AllMall-Signature: hmac-sha256=<signature>
Content-Type: application/json
  • 所有 Agent POST 请求必须携带幂等键、时间戳和签名。
  • Claim 后的请求还必须携带 X-AllMall-Claim-Token。
  • 服务端接受的时间偏差默认不超过 5 分钟。

3.2 响应格式

  "requestId": "req_20260717_001",
  "data": {},
  "error": null
}
{
  "success": false,

  "data": null,
  "error": {
    "errorCode": 5004,
    "retryable": true,
    "retryAfterSeconds": 30
  }

类型格式示例

外部系统引用opaque stringruntimeSessionRef: "mrs_store_001"
一次性令牌opaque stringconnectToken: "amct_xxx"

链路追踪stringrequestId / traceId

3.4 运行状态

statusCode内部枚举说明
10queued等待投递或领取。
15claimed已领取，等待开始。
20running执行中。
30waiting_approval等待人工审批。
35waiting_login等待用户重新登录或人机验证。
40succeeded成功完成。
45partially_succeeded部分数据集成功，仅用于允许部分成功的任务。
50failed失败。
60cancelled已取消。

3.5 重试与幂等

  • 网络超时、429、502、503、504 可重试；使用指数退避并遵守 retryAfterSeconds。
  • 相同幂等键的请求体摘要必须一致，否则返回 IDEMPOTENCY_CONFLICT。
  • 事件以 eventId 幂等；数据批次以 syncId + datasetType + batchNo 幂等。
  • Agent 不得因为响应超时而生成新的事件 ID 或批次号。

  • 只有完成确认并通过长度与 SHA-256 校验后，Artifact 才能被事件或数据批次引用。
  • Artifact URL 不直接写入事件；统一使用 artifactId。

12. 竞品建议定价 Agent 工作流

  1. SaaS 创建 competitor_pricing Task / Run，并投递待上架商品、成本约束、目标毛利、关键词、竞品数量和审批策略。
  2. SaaS 调用 POST /internal/runtime/runs，把定价任务载荷和回调地址主动投递给 Runtime。
  3. Agent 收到载荷后 Claim 任务，检查 Runtime session，回传 run_started。
  4. 按类目、属性、规格和关键词搜索候选商品，截图、去重，并过滤广告、不相关类目和不可比规格。
  5. 如果要求确认竞品清单，回传 approval_required 并暂停。
  6. 审批通过后，采集标价、到手价、券后价、运费、规格单位、销量线索、促销、评分、卖点和品牌层级。
  7. 把不同容量、数量和规格换算为可比单位价格，同时保留平台原始价格口径。
  8. 结合商品成本、平台扣点、物流成本、目标毛利和竞品价格带计算价格底线与建议区间。
  9. 对模糊销量、不可见券后价或样本不足回传 data_uncertain，不得伪造精确数据。
  10. 输出建议日常售价、建议上架试销价、建议活动价区间、价格底线、置信度和依据；上传证据后回传 run_completed。
建议价格是决策建议，不是平台写操作。Agent 不得自动创建商品、提交上架、修改 SKU 价格或报名活动。

14. 运营数据 Agent 工作流

14.1 首次全量建档

  1. 客户完成店铺绑定后，SaaS 创建 initial_full Sync / Task / Run。
  2. SaaS 调用 POST /internal/runtime/runs，主动启动运营数据 Agent 并传递 syncId、实体范围和回调地址。
  3. Agent 收到载荷后 Claim 任务，验证店铺、session、账号只读权限和同步范围。
  4. 完整枚举当前商品和 SKU；再按配置的历史窗口分页拉取订单、订单项和评论。
  5. 每页实体标准化后调用 Entity Batch 接口；持续保存平台游标、页码和批次 Checkpoint。
  6. 实体全量结束后，可继续回补经营指标；最后提交各实体数量、分页完整度和质量问题。
  7. SaaS 只有在必需实体完成后才发布初始店铺数据版本，并将水位作为后续增量起点。

14.2 周期性增量同步

  1. Scheduler 按店铺策略创建 incremental Sync，携带上次成功水位和重叠回看窗口。
  2. SaaS 经 Runtime Adapter 主动启动 Agent；主动投递失败时任务保持 queued，并可转入轮询兜底。
  3. Agent 拉取水位之后新增或变更的商品、SKU、订单和评论，并同步状态变化。
  4. Agent 同步昨日或指定日期范围的经营指标，处理退款、归因和费用的延迟变化。
  5. 完成后 SaaS 原子推进新水位；失败或部分成功不得越过未完成的必需实体水位。

14.3 指标回补

metrics_backfill 只重抓指定日期范围的统计数据，不重新枚举全部实体，适合最近 7 天退款、广告归因和平台费用回补。

只读边界：所有同步模式只更新 SaaS 数据镜像，不允许修改电商平台后台。遇到写操作页面必须停止相应步骤并记录安全事件。

21.4 通用标准化规则

  • 业务日期为 YYYY-MM-DD；时间戳为 RFC 3339，并明确店铺时区。
  • 金额使用整数最小货币单位，例如人民币分。
  • 比例使用 0 到 1 的小数；ROI 使用倍数。
  • 平台不提供、权限不足、页面失败和真实零值必须区分；非真实零值使用 null 并记录质量问题。
  • 利润、商品成本等非平台直接数据必须设置 isEstimated=true 和 calculationVersion。
  • 每个标准字段应能追溯到平台原始指标名、页面和采集时间。

22. 全量、增量与删除语义

22.1 首次全量快照

  • 同一实体类型的所有页面使用同一个 snapshotId，直到完整枚举结束。
  • Agent 必须提交源页面数量、实体数量、最终游标和 enumerationComplete=true。
  • SaaS 在全量枚举完成前将数据存入暂存版本，不替换当前可见数据。
  • 只有完整快照才能用于差异对账；页面中断、权限不足或游标失效时不得推断缺失实体已删除。

22.2 增量水位

  • 每个实体类型独立维护 sourceWatermark，不得用订单水位替代商品或评论水位。
  • Agent 查询 sourceUpdatedAt >= watermark - overlapWindow，默认重叠窗口至少 24 小时。
  • SaaS 按稳定业务键与 sourceUpdatedAt 幂等 Upsert；较旧记录不得覆盖较新状态。
  • 只有 Sync 完成且对应必需实体成功后才原子提交新水位。

22.3 状态变化与删除

平台变化recordOp标准处理
商品下架、售罄或转草稿upsert更新 productStatus，保留实体和历史关联。
订单取消、完成、退款upsert更新订单状态、金额和时间，不删除订单。
评论追加追评或商家回复upsert更新同一 externalReviewRef。
平台明确返回删除事件delete写入 Tombstone，保留审计时间和来源。
完整快照对账确认平台记录消失SaaS 对账先标记 missing_from_source；经过策略确认后再归档，不直接物理删除。

22.4 实体与指标口径

订单实体适合订单列表、商品关联和状态追踪；平台官方经营指标适合 GMV、转化率、广告归因和财务报表。SaaS 不应简单汇总订单实体来覆盖平台官方指标，两套口径必须分别保存并标记来源。

23. 失败与恢复策略

场景Agent 行为SaaS 行为
Runtime 主动投递失败尚未收到任务，无需动作。Task 保持 queued，重试 Create Run；超过阈值后切换轮询兜底或标记调度失败。
Runtime 与 SaaS 状态不一致继续按 Claim Token 和控制指令执行。查询 Runtime 状态并以 SaaS 业务状态机为准完成对账。
Session 失效回传 login_required，停止访问平台，继续心跳或释放资源。Run → waiting_login，提示用户重新登录。
平台限流遵守 Retry-After，指数退避，保留当前 Checkpoint。保持 running，记录重试次数。
单个实体或指标失败记录质量问题；非必需范围失败时继续其他范围。按必需性决定 failed 或 partially_succeeded。
全量枚举不完整保留 Checkpoint 和 snapshotId，不提交成功水位。不发布完整基线，不执行缺失实体对账。
平台游标失效从最近有效 Checkpoint 重开当前实体枚举并去重。旧批次保留，拒绝水位倒退。
Agent 崩溃新实例 Claim 后读取 Checkpoint 续跑。租约过期后允许重新投递。
用户取消心跳或控制接口收到 cancel 后尽快停止，不再写入新批次。Run / Task → cancelled。
页面结构变化上传截图或 trace，回传可重试错误。标记对应平台采集器异常。

25. 安全、审计与联调要求

  • Agent Token 必须绑定租户、Agent 类型、Runtime Provider 和允许的接口 Scope。
  • SaaS 调用 Runtime Adapter 必须使用独立的服务间身份、网络访问控制和审计日志，不得复用用户或 Agent Token。
  • Claim Token 必须绑定 Task、Run、Agent 实例和过期时间，不得跨任务复用。
  • 所有登录绑定、Claim、心跳、事件、Artifact、数据批次、审批和控制指令写入 Audit Log。
  • 买家姓名、电话、详细地址、身份证、聊天内容、物流面单和平台 Cookie 不属于运营数据采集范围；意外取得时必须在上传前删除。
  • 评论正文允许在脱敏后同步；原始评论截图若包含头像、昵称或个人信息，必须脱敏或使用受限 Artifact 策略。
  • 订单和评论实体必须受租户隔离、角色权限、访问审计和数据保留期限控制。
  • 两个 Agent 团队必须使用同一套 Header、ID 类型、状态码、事件结构、租约 SDK 和重试 SDK。
  • 联调必须覆盖重复事件、重复批次、租约过期、登录失效、审批恢复、Agent 崩溃续跑、平台限流和部分成功。
