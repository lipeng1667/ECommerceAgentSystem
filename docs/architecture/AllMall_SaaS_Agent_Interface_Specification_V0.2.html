AllMall SaaS-Agent Interface

SaaS 与 Agent 接口文档 V0.2

本文档定义 AllMall SaaS、Runtime Adapter、MuleRun、竞品调研 Agent 和日常运营 Agent 之间的统一协议，重点补齐任务领取、运行租约、心跳、控制指令、Artifact 上传，以及日常运营数据的只读采集、分批回传、断点续传和质量确认。

Login Bootstrap Competitor Research Daily Operations Task Lease Checkpoint Resume
规范结论：所有 Agent 调用 SaaS 的接口统一使用 /api/agent/*。日常运营 Agent 只能读取平台后台和回传统计数据，不得执行发货、退款、售后、评价回复、调价、投放启停、活动报名、商品修改或库存调整。

1. 接口目录

1.1 模块总览

模块范围主要调用方
登录绑定创建登录会话、解析绑定码、绑定 Runtime session。Portal、Login Bootstrap Agent。
任务运行任务主动投递或轮询领取、Claim、租约、心跳和控制指令。Runtime Adapter、两个业务 Agent。
事件与审批步骤事件、登录失效、审批请求、运行完成和审批查询。两个业务 Agent。
Artifact截图、原始数据、报告和日志的预签名上传与完成确认。两个业务 Agent。
竞品调研竞品任务输入、人工确认和最终报告。竞品调研 Agent。
日常运营同步任务上下文、数据批次、检查点、断点续传和质量完成回调。日常运营 Agent。

2. 交互架构与任务投递

2.1 组件职责

组件职责禁止事项
AllMall Portal创建任务、展示状态、处理审批和展示结果。不得直接调用电商平台或持有 Agent Key。
AllMall SaaS租户隔离、任务状态、租约、回调、数据入库、审计。不得保存电商平台账号密码。
Runtime Adapter封装 MuleRun Create Session / Create Run / Resume Run。不得绕过 SaaS 业务状态机。
Agent使用绑定的 Browser Profile 执行任务并回传证据。不得跨租户或跨店铺复用 session。

2.2 两种任务投递模式

模式流程适用阶段
runtime_pushSaaS 经 Runtime Adapter 创建 Run，并把 Task Payload 传给 Agent；Agent 随后调用 Claim。产品化默认模式。
agent_pollAgent 调用 /api/agent/tasks/next 获取候选任务，再调用 Claim。Beta、定时 Worker 或 Runtime 不支持推送时。
无论采用哪种投递模式，Agent 都必须成功 Claim 后才能执行。Task Payload 本身不是执行授权，claimToken 才是当前 Agent 实例对该 Run 的租约凭证。

3. 通用约定

3.1 Header

Authorization: Bearer <agent_access_token>
X-AllMall-Request-Id: req_20260717_001
X-AllMall-Idempotency-Key: idem_20260717_001
X-AllMall-Timestamp: 2026-07-17T10:30:00+08:00
X-AllMall-Signature: hmac-sha256=<signature>
Content-Type: application/json
  • 所有 Agent POST 请求必须携带幂等键、时间戳和签名。
  • Claim 后的请求还必须携带 X-AllMall-Claim-Token。
  • 服务端接受的时间偏差默认不超过 5 分钟。

3.2 响应格式

{

  "requestId": "req_20260717_001",
  "data": {},
  "error": null
}
{
  "success": false,
  "requestId": "req_20260717_001",
  "data": null,
  "error": {
    "errorCode": 5004,
    "retryable": true,
    "retryAfterSeconds": 30
  }
}

3.3 ID、Ref 与 Token

类型格式示例
AllMall 内部 IDint64taskId: 50001
外部系统引用opaque stringruntimeSessionRef: "mrs_store_001"
一次性令牌opaque stringconnectToken: "amct_xxx"
运行租约opaque stringclaimToken: "claim_xxx"
链路追踪stringrequestId / traceId

3.4 运行状态

statusCode内部枚举说明
10queued等待投递或领取。
15claimed已领取，等待开始。
20running执行中。
30waiting_approval等待人工审批。
35waiting_login等待用户重新登录或人机验证。
40succeeded成功完成。
45partially_succeeded部分数据集成功，仅用于允许部分成功的任务。
50failed失败。
60cancelled已取消。

3.5 重试与幂等

  • 网络超时、429、502、503、504 可重试；使用指数退避并遵守 retryAfterSeconds。
  • 相同幂等键的请求体摘要必须一致，否则返回 IDEMPOTENCY_CONFLICT。
  • 事件以 eventId 幂等；数据批次以 syncId + datasetType + batchNo 幂等。
  • Agent 不得因为响应超时而生成新的事件 ID 或批次号。

12. 竞品调研 Agent 工作流

  1. SaaS 创建 competitor_research Task / Run，并投递目标商品、关键词、竞品数量、调研维度和审批策略。
  2. Agent Claim 任务，检查 Runtime session，回传 run_started。
  3. 按关键词搜索候选商品，截图、去重、过滤广告和不相关类目。
  4. 如果要求确认竞品清单，回传 approval_required 并暂停。
  5. 审批通过后，采集价格、促销、销量线索、评价线索、标题、主图和详情页卖点。
  6. 对模糊销量、不可见券后价等问题回传 data_uncertain，不得伪造精确数据。
  7. 生成结构化数据、截图证据和最终报告，上传 Artifact 后回传 run_completed。

13. 日常运营 Agent 工作流

  1. Scheduler 默认在店铺时区次日 02:00 后创建前一日同步；用户也可手动创建。
  2. SaaS 创建 daily_operations Task / Run / Sync，并主动投递或等待 Agent 领取。
  3. Agent Claim 任务，读取同步上下文和检查点，验证店铺 session 与只读权限。
  4. 按数据集逐项进入平台后台，读取数据并保留页面、平台指标名、时区和采集时间。
  5. 将平台值标准化；每个数据集按不超过 500 条或 2 MB 分批回传。
  6. 每个数据集完成后回传步骤事件；长任务持续发送心跳。
  7. 若 Agent 重启，先查询 Checkpoint，仅从未确认批次或未完成数据集继续。
  8. 全部数据集处理后提交记录数、完整度和质量问题；SaaS 验证后发布数据版本。
只读边界：full_replace 仅表示替换 SaaS 中指定日期的数据版本，不允许修改电商平台后台。日常运营任务遇到任何写操作页面必须停止相应步骤并记录安全事件。

批次规则

  • 一个批次只能包含一个 datasetType 和一个 schemaVersion。
  • batchDigest 为 datasetType、schemaVersion、batchNo 和 records 规范化 JSON 的 SHA-256。
  • 服务端同时校验幂等键和 batchDigest；相同批次号但摘要不同返回冲突。
  • 记录级校验失败时返回拒绝记录索引和数字错误码；Agent 修正后使用新的批次号提交。
  • isLastBatch=true 只表示该数据集发送完毕，不表示整个 Sync 完成。

完成判定

  • 所有 required 数据集成功才可提交 succeeded。
  • required 数据集部分失败但已有可用数据时提交 partially_succeeded。
  • 无可发布数据或基础店铺总览失败时提交 failed，并通过事件回传失败原因。

19.1 标准化规则

  • 业务日期为 YYYY-MM-DD；时间戳为 RFC 3339，并明确店铺时区。
  • 金额使用整数最小货币单位，例如人民币分。
  • 比例使用 0 到 1 的小数；ROI 使用倍数。
  • 平台不提供、权限不足、页面失败和真实零值必须区分；非真实零值使用 null 并记录质量问题。
  • 利润、商品成本等非平台直接数据必须设置 isEstimated=true 和 calculationVersion。
  • 每个标准字段应能追溯到平台原始指标名、页面和采集时间。

19.2 数据集状态

状态含义记录数要求
pending尚未开始采集。0
running正在采集或上传批次。可大于等于 0
succeeded采集完成，允许真实无数据。可大于等于 0；无数据需说明。
unsupported平台或当前店铺版本不提供此数据。必须为 0，并提供质量问题。
permission_denied当前店铺账号无查看权限。必须为 0，并提供错误码。
failed页面、解析器或平台异常导致失败。可保留已确认批次，必须提供错误码。

20. 失败与恢复策略

场景Agent 行为SaaS 行为
Session 失效回传 login_required，停止访问平台，继续心跳或释放资源。Run → waiting_login，提示用户重新登录。
平台限流遵守 Retry-After，指数退避，保留当前 Checkpoint。保持 running，记录重试次数。
单个数据集失败记录质量问题，继续其他数据集。允许最终 partially_succeeded。
Agent 崩溃新实例 Claim 后读取 Checkpoint 续跑。租约过期后允许重新投递。
用户取消心跳或控制接口收到 cancel 后尽快停止，不再写入新批次。Run / Task → cancelled。
页面结构变化上传截图或 trace，回传可重试错误。标记对应平台采集器异常。

22. 安全、审计与联调要求

  • Agent Token 必须绑定租户、Agent 类型、Runtime Provider 和允许的接口 Scope。
  • Claim Token 必须绑定 Task、Run、Agent 实例和过期时间，不得跨任务复用。
  • 所有登录绑定、Claim、心跳、事件、Artifact、数据批次、审批和控制指令写入 Audit Log。
  • 买家姓名、电话、地址、聊天内容和平台 Cookie 不属于日常运营采集范围；意外取得时必须在上传前删除或脱敏。
  • 两个 Agent 团队必须使用同一套 Header、ID 类型、状态码、事件结构、租约 SDK 和重试 SDK。
  • 联调必须覆盖重复事件、重复批次、租约过期、登录失效、审批恢复、Agent 崩溃续跑、平台限流和部分成功。
